# RAG 路由与执行协议

## 初始检索与 Agent 反馈

1. 用完整原始请求，以 `query: ` 前缀输入本地 multilingual-e5-small，对全库检索 Top-20，不按分类树或模态筛选。
2. Agent 检查当前候选的能力、输入、输出是否能完成完整请求。候选足够时返回工作流链与媒体依赖；不足时返回 `search_needed=true`、缺失能力的 `search_query` 和理由。
3. 按 Agent 查询追加检索，最多三次（含首次）。每轮只使用当前 Top-20，不累积候选；上限仍不足时记录 `routing_failed`。
4. 保留每轮查询、候选和 Agent 判断。通信恢复复用当前轮的候选检查点，不重新执行已完成的检索。

## 生成和修复中的按需 RAG

统一 `generate_plan_with_repair` 入口在规划前调用检索判断，覆盖多阶段、单阶段、初始准备、预检修复和执行/质量反馈修复，也覆盖结构重建分支。

Agent 根据当前图、任务、错误和评价证据返回 `retrieval_required`、最多三条 `queries` 和理由。无需检索时直接继续规划；需要时检索同一冻结工作流库，每条返回 Top-20 描述以及前三份实际 API 图，作为 `repair_evidence.workflow_rag` 交给规划器。模型和节点是否安装仍由当前接口验证决定。

该入口提供参考证据，支持当前图的参数或受控结构修复；不会自动重路由整条 DAG。参考图不能代替用户媒体，也不能绕过既有修复权限、成功阶段保护和静态预检。

`execution/semantic/<case>/repair_rag/` 保存按上下文哈希索引的判断、查询和结果。相同上下文恢复时复用记录；出现新的错误、图或评价时可以再次判断和检索。没有全任务固定检索总数上限，但每次判断最多三条查询，仍受既有规划与执行轮次约束。

外部网页资料搜索保留原 `needs_search/search_queries` 机制；它与本地工作流 RAG 分开记录，不互相替代。

## 工作流准备与迭代

选中的基础 API JSON 进入共享执行器。生成 Agent 输出参数、提示词或经过校验的结构修复计划。执行器保留当前图、历史错误、实际产物和操作记录本。

最多三轮包含首次执行。生成与评价反馈可推动后续两轮修正；预检错误及通信失败不自动记成新的质量轮次。自进化及额外 Active Skill 选择在 RAG 路径关闭；库内原 Base 和既有 Skill 图作为同等的完整候选参与检索。

遇到已证实的接口/拓扑问题，可以通过共享执行器增加节点或重连，并重新预检；不要求把所有问题压缩成参数修改。多输入的独立媒体槽必须可区分，并连接到实际输出链。上游产物按 DAG 绑定，未受影响的成功阶段允许复用。

第三轮仍质量不通过时结束，不再进行不能用于下一轮执行的诊断。普通时长要求允许少量插帧边界差异；明确帧数、同步或硬上限仍需满足。

## 调度

共享 API 文件锁控制模型请求。CPU 路由、准备与待提交 GPU 队列分别记账；ComfyUI 通过原生队列顺序执行工作流。worker 启动还受系统可用内存与进程 PSS 估算约束。

通用执行器保留阶段 FIFO、prompt 提交凭据、`/history` 返回和阶段产物。质量不通过、预检失败、执行失败、评价失败及接口失败分别记录。单题异常不停止其他可运行题目。

## 恢复

- 已完成题目从 `outcome.json` 读取，正常恢复不覆盖其结果。
- 可重试的通信失败按 60 秒起始、最长 600 秒退避，最多五次恢复；保留原工作流选择、产物和迭代预算。
- 已接受的 GPU prompt 不因观察进程退出而直接重提；先核对队列、history 与提交凭据。
- 不明 worker 退出会进入 `checkpoint_review_cases`。恢复这类题目前应依据记录确认其提交状态。
- 新建本包的运行目录；不要混用固定单次检索版本或其他实验的检查点。

运行记录位于指定的本地运行目录，默认 `runs/` 被 Git 忽略。公开仓库不带任何历史案例的返回或结果。
